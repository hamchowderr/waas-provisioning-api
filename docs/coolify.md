# How stores run on Coolify

For anyone self-hosting or working on the code. The `coolify` provisioner (`src/provisioner/coolify/`) runs every store on a [Coolify](https://coolify.io) v4 server. This page explains how: what each store is made of, how the API runs commands inside it, and what each provisioner method does. To set a server up, follow [self-hosting.md](self-hosting.md).

## One store = one Coolify Service

Each store is one Coolify **Service** built from a Docker Compose file the driver renders, in project **WaaS Stores**, environment `stores` (versions in environment `versions`). Name: `store-<storeId>` (`version-<versionId>` for version sites). The name is the lookup key, so the driver keeps no Coolify ids in Postgres and every call stays idempotent: "create" first looks the name up and reuses what it finds.

```yaml
services:
  wordpress:            # serves the store; Coolify routes the store's domains here
    image: wordpress:${WP_VERSION}-php${PHP_VERSION}-apache
    environment:
      WORDPRESS_DB_HOST: db
      WORDPRESS_DB_NAME: wordpress
      WORDPRESS_DB_USER: wordpress
      WORDPRESS_DB_PASSWORD: ${SERVICE_PASSWORD_DB}   # generated by Coolify, never seen by the API
      WORDPRESS_CONFIG_EXTRA: ${WAAS_CONFIG_EXTRA}     # define() per phpConstant, plus WPCS_IS_TENANT
      WPCS_IS_TENANT: "true"
      WAAS_STORAGE_GB: "5"            # the size's quotas, read by the plan mu-plugin; none on version sites
      WAAS_EMAILS_PER_MONTH: "5000"
    volumes: [wp:/var/www/html]
    mem_limit: 512m                 # memory, CPUs and Apache workers follow the store's size
    cpus: 1
  db:
    image: mariadb:11
    environment: { MARIADB_DATABASE: wordpress, MARIADB_USER: wordpress, MARIADB_PASSWORD: ${SERVICE_PASSWORD_DB}, MARIADB_ROOT_PASSWORD: ${SERVICE_PASSWORD_ROOT} }
    volumes: [db:/var/lib/mysql]
    mem_limit: 384m
  agent:                # WP-CLI sidecar; the driver runs commands here
    image: wordpress:cli-php${PHP_VERSION}
    command: ["sleep", "infinity"]
    volumes:
      - wp:/var/www/html
      - type: bind                 # Coolify writes `content` to the file; no image registry needed
        source: ./waas/agent.php
        target: /waas/agent.php
        content: "<the driver's agent script>"
    mem_limit: 256m
```

Why a Service and not an Application plus a standalone MariaDB: one resource per store, one delete removes containers, volumes and network together (`DELETE /services/{uuid}?delete_volumes=true&delete_configurations=true&delete_connected_networks=true&docker_cleanup=true`), and Coolify gives each Service its own Docker network.

## Filling the gap: running commands

Coolify has no "exec" endpoint, but it can run a Service's **scheduled task on demand** (tasks are created through the API only; Coolify's UI form mangles programmatic commands; `container` is the compose service name): `POST /services/{uuid}/scheduled-tasks` (command, container, timeout), then `POST .../scheduled-tasks/{task}/execute`, then poll `GET .../executions` for status and output (`message`). The driver uses this as its exec: create a disabled task in container `agent`, execute it, wait, delete it. The commands are WP-CLI plus `/waas/agent.php`, a small PHP script that zips or unzips the database dump and `wp-content`, and moves files to and from object storage through pre-signed URLs. The agent container runs as `33:33`, and tasks run as uid 33; if Coolify ever runs them as root, `agent.php` drops to uid 33 (`www-data` in the Debian WordPress image; the Alpine CLI image's own `www-data` is 82) before it touches files. So all store-side logic is plain WP-CLI or one script, testable without Coolify, and no extra service runs on the host. A disabled task (Coolify still requires a valid cron, so `0 0 1 1 *`) runs on demand, and its execution's `message` holds the command's output. Coolify stores a task's command in 255 characters (longer ones fail with HTTP 500), so arguments that don't fit, such as pre-signed URLs, are first sent in 200-character chunks (`stage <id> <chunk>`) into a file in the agent's `/tmp`, which the operation (`<op> @<id>`) reads and deletes.

## Operations

| Provisioner method | Coolify calls and store-side work |
|---|---|
| `createUploadUrl` | Pre-signed `PUT` to `uploads/<versionId>.(tgz\|zip)` in object storage. No Coolify call |
| `buildVersion` | Create and deploy Service `version-<id>` (env `versions`) on the version's domain with `wordpress:<wp>-php<php>-apache`; once healthy, exec: restore the source snapshot, base snapshot or uploaded archive into it; then export its `plugins` and `themes` to `versions/<id>/code.zip` |
| `deleteVersion` | Delete the Service (all flags), delete `versions/<id>/*` |
| `copySnapshot`, `copyBaseSnapshot` | Server-side S3 copy to `snapshots/<newId>.zip`, plus a manifest naming the target version |
| `createBaseSnapshotUpload` | Pre-signed `PUT` to `base/<id>.zip`; `uri` is the object's key URL |
| `deleteBaseSnapshot` | S3 delete |
| `snapshotUpload` | Snapshot the freshly built version site into `snapshots/<id>.zip` |
| `downloadSnapshot` | S3 get |
| `createStore` | `POST /services` (`docker_compose_raw`, `urls`=[main + redirect domains] on `wordpress`, `instant_deploy`), env: WP/PHP version, rendered constants, first user (see Security). Wait until `running:healthy`. Exec: restore the snapshot (`wp db import`, unzip `wp-content`), overlay the version's code, `wp search-replace` old home URL to `https://<mainDomain>`, apply `wpOptions`, create the user, install the WaaS mu-plugin. Then delete the one-time env values |
| `setDomains` | `PATCH /services/{uuid}` `urls`, restart so Traefik picks up the routers; exec: set `home`/`siteurl` (and `search-replace` when the main domain changed). The mu-plugin 301s any host other than `home`'s to it |
| `updateStore` | Options: exec `wp option update`. Constants: `PATCH .../envs/bulk` with `WAAS_CONSTANTS_B64` rendered from the store's complete set (the job passes it whole: Coolify's API does not return variable values to a token without the sensitive-data permission, so the driver never reads them back), restart |
| `moveStore` | Change the image tag in the compose (`PATCH`, base64), redeploy, exec: overlay the new version's code, `wp core update-db` |
| `snapshotStore` | Exec: `wp db export` + zip `wp-content`, `PUT` to `snapshots/<id>.zip` |
| `restoreStore` | Exec: download, `wp db import`, replace `wp-content`, `search-replace` back to the store's domain |
| `backupStore` | Same as snapshot, to `backups/<id>.zip`; size from S3 `HEAD` |
| `restoreDeletedStore` | `createStore` with the backup as the source and no user |
| `deleteBackup` | S3 delete |
| `suspendStore` | Exec: write `wp-content/.waas-suspended`. The mu-plugin and an `.htaccess` block (outside WordPress's markers) answer **503** with a plain page for every path, including `wp-cron.php`, `/wp-json/` and static files. Database and domains stay. Instant, no redeploy |
| `resumeStore` | Exec: remove the flag file |
| `deleteStore` | `DELETE /services/{uuid}` with all four cleanup flags; then confirm by name lookup that it is gone |
| `ensureStoreCron` | See [Store cron](#store-cron). Also the last step of `createStore` |

**Restarts.** Coolify fills in container statuses from a periodic check, so for up to a minute after `POST /services/{uuid}/restart` they still read the old `running:healthy`. The driver therefore first waits until some status shows the restart (not running healthy), then waits for healthy and pings the agent, so the next command never runs in containers about to stop. If no status shows the restart within 3 minutes (a restart quicker than Coolify's check), it goes on to wait for healthy.

<a id="store-cron"></a>**Store cron.** WP-cron normally runs only when a page is loaded (and Action Scheduler's async runner only from wp-admin requests), so on a quiet store renewals, dunning and other scheduled jobs would run late or never. Stores therefore set `DISABLE_WP_CRON` (in `WORDPRESS_CONFIG_EXTRA`, after the phpConstants, so a constant of that name wins) and each store Service has one enabled scheduled task named `wp-cron` in container `agent`, every minute (`* * * * *`), timeout 300 s:

```
[ -f /var/www/html/wp-content/.waas-suspended ] || flock -n /tmp/waas-cron.lock sh -c "wp --path=/var/www/html action-scheduler run --quiet; wp --path=/var/www/html cron event run --due-now --quiet"
```

It runs as the agent container's user (33, like WordPress), skips a suspended store (a suspended store runs no cron), and `flock` keeps a slow run from overlapping the next one. No single quotes: Coolify wraps the command in `sh -c '...'`. `createStore` adds it once the store is configured; it is found by name, so a retry reuses it and a differing or duplicate `wp-cron` task is replaced. On startup the API runs `ensureStoreCron` for every live (Done) store in the background; a store that has no `wp-cron` task yet predates this, so its compose is re-rendered (for `DISABLE_WP_CRON`) and it is restarted once before the task is added. Version sites take no orders and get no task; they share the compose, so their WP-cron does not run. Cost: Coolify records one execution per store per minute (~1,440 rows a day per store, in `scheduled_task_executions` in Coolify's own Postgres).

**Pruning the executions.** Coolify trims that table itself, but only to 60 days: its scheduler runs `php artisan cleanup:database --yes` daily (`app/Console/Kernel.php`, not on dev instances), which deletes `scheduled_task_executions` rows older than `--keep-days` (default 60; no setting in the UI or API changes it). That leaves ~86,000 rows per store. The API cannot delete executions (no endpoint), so keep 7 days with one daily host cron job (step 4 of [self-hosting.md](self-hosting.md)). In Coolify → Servers → your server → Terminal (a root shell on the host), run `crontab -e` and add:

```
23 4 * * * docker exec coolify-db psql -U coolify -d coolify -c "DELETE FROM scheduled_task_executions WHERE created_at < now() - interval '7 days'" > /dev/null 2>&1
```

Run the `docker exec ...` part once by hand first: it prints `DELETE <n>`. It touches only execution history (status and output of past runs), never tasks, and covers every Coolify resource's tasks, not only stores'. (`docker exec coolify php artisan cleanup:database --yes --keep-days=7` would also work, but it trims sessions, the activity log and deployment history to 7 days as well.)

Why suspend with a flag rather than `POST /services/{uuid}/stop`: a stopped Service drops its Traefik routers, so its domains answer Traefik's 404, not the 503 a suspended store must answer with. The 503 body is one shared "website unavailable" page (the agent's `render_unavailable_page`), branded per suspend and written to `wp-content/waas-unavailable.html`: Apache serves it as the 503 error document, and the guard mu-plugin serves it if a request reaches PHP. A later option, for stores suspended for long: stop the Service and point the domains at one shared "store unavailable" responder.

## Object storage

All archives live in one private S3-compatible bucket, with these prefixes: `uploads/`, `base/`, `versions/`, `snapshots/`, `backups/`. The API signs requests itself (AWS SigV4, no SDK) and hands the store's agent pre-signed URLs valid for 15 minutes, so stores never hold bucket credentials. Any S3-compatible service works; Cloudflare R2 has no egress fees. Keep the bucket off the server the stores run on, so a dead disk does not take the backups with it.

## Resource limits

Each store has a size (`tenants.size`, set with `size` on POST and PUT `/v1/tenants`; `src/plans.ts`), which sets its WordPress container's limits and its plan's quotas:

| Size | CPUs | WordPress memory | Apache workers | Storage | Emails a calendar month (UTC) |
|---|---|---|---|---|---|
| small (default) | 1 | 512 MB | 8 | 5 GB | 5,000 |
| medium | 2 | 512 MB | 16 | 10 GB | 20,000 |
| large | 4 | 768 MB | 32 | 25 GB | 50,000 |

More visitors at once than workers wait in Apache's queue instead of running the store out of memory. MariaDB 384 MB and agent 256 MB (it loads WordPress with all plugins for the store's cron every minute) for every size. Version sites run as small, without quotas. Limits cap a busy or broken store; they are not reservations. Measured use is about 273 MB per small store when warm.

The quotas reach WordPress as `WAAS_STORAGE_GB` and `WAAS_EMAILS_PER_MONTH` and are enforced by the agent's `mu-plugins/waas-plan.php`. Storage is wp-content (without `wp-content/cache`) plus the database, measured by a daily WP-cron event and counted up with each upload in between (1 GB = 1024³ bytes); an upload past it is refused with a message to delete files or move to a bigger plan. Email counts what WordPress sent this calendar month; past it `wp_mail` sends nothing until the next month. The store's administrators see a notice from 80% of either quota. The agent's `usage` operation reports storage (measured then), and this month's emails, for later use by the API. A size change (PUT) re-renders the compose file, restarts the store once and reinstalls the agent's files. Disk: ~150 MB for core and images per store (images are shared between stores on one version) plus the store's uploads and database. To grow past one server, see [self-hosting.md](self-hosting.md).

## Page cache

Every store has a page cache, installed by the agent with its other files (`install_cache` in `agent.php`): `wp-content/advanced-cache.php` (loaded because the compose file turns on `WP_CACHE`) and `mu-plugins/waas-cache.php`. A logged-out visitor's page is saved under `wp-content/cache/waas-pages/` and the next visitors get that copy before WordPress and its plugins load (response header `X-WaaS-Cache: hit`). Never cached: requests with a query string or any cookie other than a few analytics ones (logged-in users, carts, password-protected posts), `wp-admin`, `wp-json` and `.php` URLs, FluentCart's cart, checkout, receipt and account pages, and any page that is not a 200, sets a cookie or says `no-cache`/`private`. Saved pages expire after 10 minutes and are all cleared when content changes (posts, terms, menus, comments, theme, plugins, FluentCart products and paid orders) and on every agent install (restore, configure, suspend). A drop-in another cache plugin wrote is left alone, and ours then stays out of the way.

Measured on a local copy with FluentCart, FluentCRM, Fluent Forms and Rank Math and the live limits: about 400 cached pages a second with no errors at 50 visitors at once, against about 14 a second through WordPress, with memory staying under 180 MB.

## Store setup

`STORE_SETUP` (`provisioner.ts`) numbers what the compose file and the agent's files give a store; a store's Coolify description records the number it has and the size its compose file was rendered with (`WaaS store, version <id>, setup <n>, size <size>`; a description without a size is small). On every API start, `ensureStoreSetup` brings each older live store, and each store whose size differs from its tenant's, to the current setup at that size: the new compose file, one restart, then `configure` to reinstall the agent's files. Bump `STORE_SETUP` with any such change that existing stores should get. Setup 2 is the Apache worker cap and the page cache; setup 3 is sizes and the plan mu-plugin.

## Security

- **Isolation between stores.** Each store has its own containers, volumes, Docker network and generated database password. Store containers are not on Coolify's shared `coolify` network (`connect_to_docker_network: false`), so they cannot reach the provisioning API, its Postgres or other apps on the server by container name. They share the kernel with everything else on the server: this is container isolation. Stores that need stronger separation belong on a server of their own.
- **No tenant shell.** The agent runs only commands the driver composes from validated input: ids are UUIDs, domains pass `normalizeDomain`, options and constants travel as JSON in an environment variable or base64 argument, never spliced raw into a shell string.
- **Secrets.** Private constants and the first user's password stay encrypted with `SECRETS_KEY` in Postgres and are decrypted only in the job that needs them. They reach the store as Coolify environment variables (encrypted at rest by Coolify), never in a scheduled-task command, a URL or a log line. The first user's password variable is deleted after the store's first boot. Database passwords are generated by Coolify (`SERVICE_PASSWORD_*`) and never pass through the API; the driver never reads them back. Pre-signed URLs do appear in task commands; they last 15 minutes and the task is deleted after it runs. The driver's errors carry Coolify's status and message, not request bodies.
- **Coolify token.** Coolify tokens are team-wide (no per-project scope). The API's token needs `read`, `read:sensitive`, `write` and `deploy` (without `read:sensitive` Coolify hides the agent's output); it should not have `root`. The driver refuses to touch any resource outside the configured project.
- **Cleanup on failure.** Every method is idempotent by name. A failed `createStore` leaves the Service for the queue's retry to reuse; a tenant that ends Failed is removed with `deleteTenant`, which deletes the Service and its volumes.

## What Coolify cannot do, and the fill

| Gap | Fill |
|---|---|
| Exec in a container | On-demand scheduled task in the `agent` sidecar |
| Snapshot to S3 with files and DB together | `agent.php` with WP-CLI, pre-signed URLs |
| Suspend with 503 | Flag file read by an mu-plugin and `.htaccess` |
| Redirect domains with 301 | mu-plugin, by comparing the host to `home` |
| Wildcard certificates | You configure a DNS-01 resolver in Traefik |
| Server specs | The operator knows them; Coolify's API does not report them |
