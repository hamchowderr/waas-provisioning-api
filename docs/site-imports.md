# Moving a site in

For whoever runs the API. A WordPress site running on another host can be moved into a new store. The store keeps the site's own plugins and themes instead of getting its version's code, so the site looks and works the way it did.

## How it goes

1. **A store waits for the site.** `POST /v1/tenants` with `"uploadCustomSnapshot": true` (the dashboard's *Move a site in*, or the connector's `import_site`) creates the tenant Pending, with no snapshot and `own_code = true`, and a `tenant_imports` row. The answer has an `importCode` (`AP1.` + base64url of `{"u": <API address>, "t": <token>}`). Only the token's sha256 is stored. The code works for 7 days, until the move starts; `POST /v1/tenants/import-code` gives a new one (the old one stops working). The tenant shows `waitingForSite: true`, and every change to it except deleting is refused with 409 until the move is done.
2. **The owner runs the AnyPress Export plugin** on the old site (`GET /imports/plugin.zip` downloads the latest stable release; source in waas-plugins `packages/anypress-export`). Under Tools → Move to AnyPress they paste the code, or run `wp anypress-export send <code>`. The plugin works in short steps that survive timeouts: it dumps the database, packs `database.sql`, `anypress.json` and `wp-content/` into one gzipped tar in the uploads folder, uploads it in parts, and starts the move. The old site is never changed.
3. **The plugin's calls** take the code in the JSON body and no API key (the token is the credential), and are not request-logged:
   - `POST /imports/upload` answers a 12-hour upload link (`s3://$S3_BUCKET/imports/<store id>`), the most the archive may hold (the store size's storage, at most 5 GB, one PUT's limit) and the store's name, size and address.
   - Uploads in parts (AnyPress Export 1.2.0 and later), so a dropped connection costs one part and an upload carries on where it stopped: `POST /imports/upload/parts/start` with the archive's `bytes` starts an S3 multipart upload to the same place and answers its `uploadId`, the `partSize` (16 MB, more for archives over 160 GB) and `partCount`. `POST /imports/upload/parts` with the `uploadId` and up to 100 part numbers answers the parts already uploaded and a 12-hour link to PUT each one asked for. `POST /imports/upload/parts/finish` joins them; every part from 1 to the last must be there. Unfinished uploads are removed by the bucket's own clean-up of incomplete multipart uploads (R2: after 7 days).
   - `POST /imports/start` checks the uploaded size, records what the plugin says about the old site (`tenant_imports.source`: home, WordPress and PHP versions, table prefix, size) and queues `tenant.create`.
   - `POST /imports/status` answers `waiting`, `moving`, `done` (with the store's `url`, `onHold` and `siteReport`) or `failed` (with a `reason`). Once the move has run, `warnings` lists anything the owner should check (below).
4. **The store is built from the archive.** `tenant.create` makes the store as usual, then the agent's `restore` with `import: true`: it unpacks the archive, removes what must not come along (host drop-ins such as `object-cache.php` and `advanced-cache.php`, backup plugins' folders, the export plugin, managed hosts' must-use plugins, and page builders' CSS caches, see `IMPORT_DROP` in `agent.php`), loads the database and renames its tables to the store's prefix. Only WordPress's own prefixed keys are renamed with them (the `user_roles` option, and each user's capabilities, level, screen settings and preferences): a plugin's option that happens to start with the old prefix keeps its name, so a prefix such as `site_` leaves `site_icon` and `site_logo` alone.
5. **The site's addresses move to the store.** Every link to the old address becomes the store's: over http and https, on the `www.` and bare forms of its host, with its port and path (a site at `https://old.com/blog` comes to the store's root), and as written, JSON-escaped (`https:\/\/old.com`, as page builders keep them) and URL-encoded (`https%3A%2F%2Fold.com`). A custom content address (Bedrock's `/app`, when the export plugin sends `contentUrl` in `anypress.json`) becomes the store's `/wp-content`. Post GUIDs are left as they were. An upload folder or upload address that points outside the store (`upload_path`, `upload_url_path`) and Elementor's cached CSS are cleared. Then `update-db` and `configure` run (the store's address, its constants, the owner's user). The options sent when the store was created are not written over the moved site's own (its title and settings stay); send them with an update after the move if you want them.
6. **The site is checked.** The store loads the moved site's home page and `/wp-login.php` from inside its own network, and loads WordPress once with every plugin and the theme. A page that fails, or a PHP fatal error, does not stop the move: the store is built, and the warning (with the first PHP error, without server paths) is in `/imports/status` and the dashboard, so the owner can fix or switch off the plugin at fault. The warnings also say when the old site ran another PHP than the store (8.3), or a newer WordPress than the store's version.
7. **What's on the site is listed.** The same check counts, with plugins switched off and a few database queries, what the moved site holds: its active plugins and, for form, shop, CRM, booking, support, affiliate and community plugins (Contact Form 7 with Flamingo, WPForms, Gravity Forms, Ninja Forms, Formidable, Forminator, Elementor Pro forms; WooCommerce with its orders, guest orders and active subscriptions, Easy Digital Downloads, SureCart; Mailchimp for WordPress, MailPoet, Newsletter; Amelia, Bookly; Awesome Support, SupportCandy; AffiliateWP, SliceWP; BuddyPress, BuddyBoss, bbPress; and the Fluent plugins themselves), how many forms, entries, products, orders, contacts, tickets and so on each one has, and how many pages still carry their form shortcodes or blocks. Only counts are read: never the data, and never a payment key (only whether a payment method has live keys). The report (`siteReport`, built in `src/sitereport.ts`) says for each plugin whether a Fluent plugin can bring its data in (`fluentRoute`: `native`, `native-pro`, `addon` or `none`, and `needsPro`), what a switch would lose (`willLose`) and what to fix or decide first (`blockers`: WooCommerce orders not in HPOS tables, Flamingo off with Contact Form 7 entries, fields only Fluent Forms Pro brings in, active subscriptions, live payment keys). It is in `/imports/status` once the move is done, in `GET /v1/tenants/import`, in the dashboard's store page and in the connector's `get_stores` with `move_in`. A count that fails is left out and noted; it never fails the move.
8. **The store is on hold until it goes live** (`onHold: true` on the tenant). The old site usually still runs while the owner looks over the new one, so the moved store must not act as if it were the live site:
   - its scheduled tasks don't run (no WP-cron or Action Scheduler: no subscription renewals, order clean-ups, newsletter or feed syncs, backups to the old site's storage);
   - it sends email only to its administration address and to the people with an account on its storefront; every other email is held, not sent, and the last 20 held (subject, and recipients partly hidden) are kept in the `waas_hold_mail` option;
   - it asks search engines not to index it (`noindex` in the page and an `X-Robots-Tag` header, and a `robots.txt` that disallows everything);
   - its administrators see a notice that it is on hold.

   When the owner is ready (usually once the domain points at the store), `POST /v1/tenants/go-live` (the dashboard's *Go live*, `POST /admin/tenants/:id/go-live`, or the connector's `store_status` with `go_live`) ends the hold: cron starts, email goes to everyone and it may be indexed. Webhooks get `tenant.live`. Restoring, rolling back or moving a held store keeps it held, and a held store restored after deletion comes back held.
9. **Afterwards** the store is an ordinary store that keeps its own code: moving it to another version, rolling it back, restoring it and restoring it after deletion never replace its plugins and themes (`keepsOwnCode: true`). Its updates are the site owner's, as on any WordPress. The upload is deleted once the store is Done.

## Copying the site with Reprint instead

The other way in needs no export: the store copies the old site from its host with WordPress's own [Reprint](https://wordpress.org/plugins/reprint/) (its Reprint Server plugin on the old site, and the official `reprint.phar` client in the store's agent). The upload above stays for sites the store can't reach.

1. **Every waiting store has a Migration Token.** `GET /v1/tenants/import` answers `migrationToken`: the public half of an RSA key made for the store (`tenant_imports.reprint_key`, the private half encrypted under `SECRETS_KEY`). A new import code keeps the same key.
2. **The owner authorizes it on the old site.** They install Reprint (Plugins → Add New Plugin, search "Reprint"), open Tools → Reprint Server, paste the token under *Authorize a client to copy this site* and choose **Authorize client**.
3. **The copy starts.** `POST /v1/tenants/import-reprint` with `{"siteUrl": "https://old.example.com"}` (https only) records the address and queues `tenant.create`. The agent's `restore` gets `reprint: {site, key}` instead of an archive link: it downloads the pinned client (`REPRINT_VERSION` and its SHA-256 in `agent.php`), runs `pull-files` (only `wp-content`) and `db-pull` against `<site>/?reprint-api`, and goes on exactly as with an export (step 4 onwards). Reprint's progress is kept in the agent container's `/tmp/waas-reprint`, so a job attempt that runs out of time (25 minutes) carries on where it stopped in the next one; it is removed once the copy is in. The old site's Reprint plugin and its access settings are left behind.
4. **Copy again before going live.** While the store is on hold, the same call copies the old site again, so orders, posts and form entries made there since come along. It replaces the store's content: changes made on the store meanwhile are lost. A copy again that can't fetch the site leaves the store as it was (still Done and held) and `reason` says why. Once live, the store can't be copied again.

A copy that fails (Reprint's error code is in the job's error) gives `reason` in plain words: Reprint not installed at that address, the token not authorized yet, a security service (Cloudflare's browser challenge, Wordfence) in the way, the address not reachable. The owner can fix it and start the copy again, or move the site with the AnyPress Export plugin instead: its code still works after a failed copy.

## When a move fails

`/imports/status` and the dashboard give a `reason` the owner can act on: the export is missing its database or files, the upload could not be read (run the export again), the database could not be imported, the database has two sets of WordPress tables whose names collide, or the site is a multisite network. Anything else says to contact support; the full error is on the Jobs page.

## Limits

- Multisite networks are refused by the plugin and by the store.
- The archive must fit the store's storage (10, 20 or 30 GB by size) and 5 GB in all. A larger site needs a larger size, or its media moved separately.
- The old host needs PHP 7.4+, zlib and cURL, and room in its uploads folder for the archive.
- `wp-config.php` is not moved: licence keys and other constants kept there (and its salts, so everyone signs in again) must be added to the store's constants.
- Links to the old site inside theme and plugin files (CSS and JavaScript) are not rewritten; page builders' CSS caches are cleared and written again.
- Changes on the old site after the export (new orders, form entries) are not in the store. A site copied with Reprint can be copied again before it goes live.
- Store email, domains, backups and the cron task are the store's, as for any store. The old site's address keeps working where it is until its DNS is moved.

## Housekeeping

The maintenance job deletes stores whose import code expired before the move started, and anything uploaded for them. They never ran, so nothing on the store host is touched.

## Releasing the plugin

The plugin is released like our others: tag `anypress-export-v<x.y.z>` on main in waas-plugins. `GET /imports/plugin.zip` follows the stable channel.
