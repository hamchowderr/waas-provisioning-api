# ADR 0001: Coolify Provisioner for normal stores

Status: **Proposed**, waiting for the owner's go. Date: 2026-10-07. Issue: `waas-api-2hl.10`.

## Context

The API does all store-side work through `Provisioner` (`src/provisioner/provisioner.ts`). The only implementation is the in-memory `FakeProvisioner`. The platform is general WordPress-as-a-Service; most stores sell ordinary products. `docs/hosting.md` covers regulated stores, which cannot run on the Hostinger VPS; that host question (`waas-api-2hl.4`, `waas-api-2hl.7`) stays open. This ADR covers **normal stores only**, on the existing Coolify (v4.3.23) on the Hostinger VPS. The driver takes the server as configuration, so the same code can later drive a second server, including a host that accepts regulated stores.

| Servers | One: `localhost` (`sq3c52uczu81384adrlo7w77`), the Coolify host, public IP `191.101.15.236` (and IPv6) |

## Decision

### One store = one Coolify Service

Each store is one Coolify **Service** built from a Docker Compose file the driver renders, in project **WaaS Stores**, environment `stores` (versions in environment `versions`). Name: `store-<storeId>` (`version-<versionId>` for version sites). The name is the lookup key, so the driver keeps no Coolify ids in Postgres and every call stays idempotent: "create" first looks the name up and reuses what it finds.

```yaml
services:
  wordpress:            # serves the store; Coolify routes the store's domains here
    image: wordpress:${WP_VERSION}-php${PHP_VERSION}-apache
    environment:
      WORDPRESS_DB_HOST: db
      WORDPRESS_DB_NAME: wordpress
      WORDPRESS_DB_USER: wordpress
      WORDPRESS_DB_PASSWORD: ${SERVICE_PASSWORD_DB}   # generated by Coolify, never seen by the API
      WORDPRESS_CONFIG_EXTRA: ${WAAS_CONFIG_EXTRA}     # define() per phpConstant, plus WPCS_IS_TENANT
      WPCS_IS_TENANT: "true"
    volumes: [wp:/var/www/html]
    mem_limit: 512m
    cpus: 1
  db:
    image: mariadb:11
    environment: { MARIADB_DATABASE: wordpress, MARIADB_USER: wordpress, MARIADB_PASSWORD: ${SERVICE_PASSWORD_DB}, MARIADB_ROOT_PASSWORD: ${SERVICE_PASSWORD_ROOT} }
    volumes: [db:/var/lib/mysql]
    mem_limit: 384m
  agent:                # WP-CLI sidecar; the driver runs commands here
    image: wordpress:cli-php${PHP_VERSION}
    command: ["sleep", "infinity"]
    volumes:
      - wp:/var/www/html
      - type: bind                 # Coolify writes `content` to the file; no image registry needed
        source: ./waas/agent.php
        target: /waas/agent.php
        content: "<the driver's agent script>"
    mem_limit: 256m
```

Why a Service and not an Application plus a standalone MariaDB: one resource per store, one delete removes containers, volumes and network together (`DELETE /services/{uuid}?delete_volumes=true&delete_configurations=true&delete_connected_networks=true&docker_cleanup=true`), and Coolify gives each Service its own Docker network.

### Filling the gap: running commands

Coolify has no "exec" endpoint, but it can run a Service's **scheduled task on demand** (tasks are created through the API only; Coolify's UI form mangles programmatic commands; `container` is the compose service name): `POST /services/{uuid}/scheduled-tasks` (command, container, timeout), then `POST .../scheduled-tasks/{task}/execute`, then poll `GET .../executions` for status and output (`message`). The driver uses this as its exec: create a disabled task in container `agent`, execute it, wait, delete it. The commands are WP-CLI plus `/waas/agent.php`, a small PHP script that zips or unzips the database dump and `wp-content`, and moves files to and from object storage through pre-signed URLs. The agent container runs as `33:33`, and tasks ran as uid 33 in the live check; if Coolify ever runs them as root, `agent.php` drops to uid 33 (`www-data` in the Debian WordPress image; the Alpine CLI image's own `www-data` is 82) before it touches files. So all store-side logic is plain WP-CLI or one script, testable without Coolify, and no extra service runs on the host. Verified live on 4.3.23: a disabled task (Coolify still requires a valid cron, so `0 0 1 1 *`) runs on demand, and its execution's `message` holds the command's output. Coolify stores a task's command in 255 characters (longer ones fail with HTTP 500), so arguments that don't fit, such as pre-signed URLs, are first sent in 200-character chunks (`stage <id> <chunk>`) into a file in the agent's `/tmp`, which the operation (`<op> @<id>`) reads and deletes.

### Operations

| Provisioner method | Coolify calls and store-side work |
|---|---|
| `createUploadUrl` | Pre-signed `PUT` to `uploads/<versionId>.(tgz\|zip)` in object storage. No Coolify call |
| `buildVersion` | Create and deploy Service `version-<id>` (env `versions`) on the version's domain with `wordpress:<wp>-php<php>-apache`; once healthy, exec: restore the source snapshot, base snapshot or uploaded archive into it; then export its `plugins` and `themes` to `versions/<id>/code.zip` |
| `deleteVersion` | Delete the Service (all flags), delete `versions/<id>/*` |
| `copySnapshot`, `copyBaseSnapshot` | Server-side S3 copy to `snapshots/<newId>.zip`, plus a manifest naming the target version |
| `createBaseSnapshotUpload` | Pre-signed `PUT` to `base/<id>.zip`; `uri` is the object's key URL |
| `deleteBaseSnapshot` | S3 delete |
| `snapshotUpload` | Snapshot the freshly built version site into `snapshots/<id>.zip` |
| `downloadSnapshot` | S3 get |
| `createStore` | `POST /services` (`docker_compose_raw`, `urls`=[main + redirect domains] on `wordpress`, `instant_deploy`), env: WP/PHP version, rendered constants, first user (see Security). Wait until `running:healthy`. Exec: restore the snapshot (`wp db import`, unzip `wp-content`), overlay the version's code, `wp search-replace` old home URL to `https://<mainDomain>`, apply `wpOptions`, create the user, install the WaaS mu-plugin. Then delete the one-time env values |
| `setDomains` | `PATCH /services/{uuid}` `urls`, restart so Traefik picks up the routers; exec: set `home`/`siteurl` (and `search-replace` when the main domain changed). The mu-plugin 301s any host other than `home`'s to it |
| `updateStore` | Options: exec `wp option update`. Constants: `PATCH .../envs/bulk` with `WAAS_CONSTANTS_B64` rendered from the store's complete set (the job passes it whole: Coolify's API does not return variable values to a token without the sensitive-data permission, so the driver never reads them back), restart |
| `moveStore` | Change the image tag in the compose (`PATCH`, base64), redeploy, exec: overlay the new version's code, `wp core update-db` |
| `snapshotStore` | Exec: `wp db export` + zip `wp-content`, `PUT` to `snapshots/<id>.zip` |
| `restoreStore` | Exec: download, `wp db import`, replace `wp-content`, `search-replace` back to the store's domain |
| `backupStore` | Same as snapshot, to `backups/<id>.zip`; size from S3 `HEAD` |
| `restoreDeletedStore` | `createStore` with the backup as the source and no user |
| `deleteBackup` | S3 delete |
| `suspendStore` | Exec: write `wp-content/.waas-suspended`. The mu-plugin and an `.htaccess` block (outside WordPress's markers) answer **503** with a plain page for every path, including `wp-cron.php`, `/wp-json/` and static files. Database and domains stay. Instant, no redeploy |
| `resumeStore` | Exec: remove the flag file |
| `deleteStore` | `DELETE /services/{uuid}` with all four cleanup flags; then confirm by name lookup that it is gone |
| `ensureStoreCron` | See [Store cron](#store-cron). Also the last step of `createStore` |

<a id="store-cron"></a>**Store cron.** WP-cron normally runs only when a page is loaded (and Action Scheduler's async runner only from wp-admin requests), so on a quiet store renewals, dunning and other scheduled jobs would run late or never. Stores therefore set `DISABLE_WP_CRON` (in `WORDPRESS_CONFIG_EXTRA`, after the phpConstants, so a constant of that name wins) and each store Service has one enabled scheduled task named `wp-cron` in container `agent`, every minute (`* * * * *`), timeout 300 s:

```
[ -f /var/www/html/wp-content/.waas-suspended ] || flock -n /tmp/waas-cron.lock sh -c "wp --path=/var/www/html action-scheduler run --quiet; wp --path=/var/www/html cron event run --due-now --quiet"
```

It runs as the agent container's user (33, like WordPress), skips a suspended store (the contract stops a suspended store's cron), and `flock` keeps a slow run from overlapping the next one. No single quotes: Coolify wraps the command in `sh -c '...'`. `createStore` adds it once the store is configured; it is found by name, so a retry reuses it and a differing or duplicate `wp-cron` task is replaced. On startup the API runs `ensureStoreCron` for every live (Done) store in the background; a store that has no `wp-cron` task yet predates this, so its compose is re-rendered (for `DISABLE_WP_CRON`) and it is restarted once before the task is added. Version sites take no orders and get no task; they share the compose, so their WP-cron does not run. Cost: Coolify records one execution per store per minute.

Why suspend with a flag rather than `POST /services/{uuid}/stop`: a stopped Service drops its Traefik routers, so its domains answer Traefik's 404, not the 503 the contract asks for. A later option, for stores suspended for long: stop the Service and point the domains at one shared "store unavailable" responder.

### Versions, snapshots and object storage

All archives live in one **S3-compatible bucket**, private, with these prefixes: `uploads/`, `base/`, `versions/`, `snapshots/`, `backups/`. The API signs requests itself (AWS SigV4, no SDK) and hands the store's agent pre-signed URLs valid for 15 minutes, so stores never hold bucket credentials.

Recommendation: **Cloudflare R2**. No egress fees, off the VPS (a dead disk does not take the backups with it), and the owner already uses Cloudflare. The alternative is a self-hosted S3 server as a Service in `WaaS Stores` (the MinIO image would not start on this host on 2026-10-07; RustFS did, and served the smoke test): no new account, but backups then sit on the same disk as the stores.

The owner creates: an R2 bucket (e.g. `waas-stores`), an R2 API token with Object Read & Write on that bucket only, and a lifecycle rule deleting `uploads/` after 7 days. The API gets `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` (and `S3_REGION=auto`).

### Store domains and TLS

Today `STORES_DOMAIN=stores.invalid`. Proposed: stores at `t-<id8>.<stores domain>`, versions at `<slug>.<versions domain>`, on a domain in the owner's Cloudflare account, e.g. `stores.<domain>` and `versions.<domain>`, or a separate registered domain (better: a store's abuse report then cannot touch Otaku's own domain and cookies, and Let's Encrypt's 50-certificates-a-week limit counts per registered domain).

Certificates, in two steps:

1. **Now, no token needed:** per-hostname certificates through the existing HTTP-01 resolver. Works as soon as the wildcard `A` record exists. Fine below ~40 new stores a week.
2. **Wildcard (`*.stores.<domain>`) through DNS-01:** add a second resolver to Traefik with Cloudflare's DNS challenge, and a dynamic-config router that requests the wildcard. Store routers then match that certificate. Custom domains keep HTTP-01.

Owner steps:

1. In Cloudflare DNS for the chosen domain: `A *.stores` → `191.101.15.236`, `AAAA *.stores` → `2a02:4780:10:446c::1`, and the same for `*.versions`. **DNS only (grey cloud)**, so HTTP-01 for custom domains and Traefik's TLS keep working.
2. For the wildcard (step 2 above): create a Cloudflare API token with **Zone:DNS:Edit** on that zone only. In Coolify → Servers → localhost → Proxy, add `CF_DNS_API_TOKEN=<token>` to the proxy's environment and these lines to its command, then restart the proxy (the owner does this; the API never sees the token):
   ```
   - '--certificatesresolvers.cloudflare.acme.dnschallenge=true'
   - '--certificatesresolvers.cloudflare.acme.dnschallenge.provider=cloudflare'
   - '--certificatesresolvers.cloudflare.acme.storage=/traefik/acme.json'
   ```
   and a dynamic file (Proxy → Dynamic Configurations) `waas-stores-wildcard.yaml` that asks the `cloudflare` resolver for `stores.<domain>` with SAN `*.stores.<domain>`. Restarting the proxy briefly interrupts every site on the VPS; pick a quiet time.
3. Set `STORES_DOMAIN` and `VERSIONS_DOMAIN` on the API.

Custom domains: the customer adds a `CNAME` to their store's `t-<id8>.stores.<domain>` (or an `A` record to the IP for an apex domain); `setDomains` adds it to the Service and Traefik gets its certificate over HTTP-01. The API should check DNS before calling `setDomains`, so a failed challenge does not spend the rate limit (a follow-up, not in this change).

**For now (owner's decision, 2026-10-07)** stores and versions use sslip.io, which needs no DNS: `STORES_DOMAIN=191.101.15.236.sslip.io` and `VERSIONS_DOMAIN=191.101.15.236.sslip.io`, so a store answers on `t-<id8>.191.101.15.236.sslip.io` with a real HTTP-01 certificate. sslip.io is fine for testing and early stores, but it is a third party's DNS and Let's Encrypt limits certificates per registered domain, so move to an owned domain before many stores go live.

#### Switching to an owned domain later

The domain is configuration only; no code changes.

1. DNS for the new domain as above (`*.stores` and `*.versions`, A and AAAA to the VPS, grey cloud).
2. Set `STORES_DOMAIN` and `VERSIONS_DOMAIN` on the waas-api app and redeploy. New stores and versions get names under the new domain at once.
3. Existing stores keep their old base domain until moved. For each, add the new base domain with `addTenantDomain` and make it main with `setMainDomain`: `setDomains` adds the Traefik routers, the certificate is issued over HTTP-01, and `home`/`siteurl` and the database URLs are rewritten (`wp search-replace`). The old sslip.io name then 301s to the new one; remove it with `removeTenantDomain` once nothing links to it. Customers' custom domains are untouched.
4. Version sites: create new versions on the new domain, or move the existing ones the same way.
5. Optional, later: the wildcard certificate (step 2 of the certificate plan above).

### Resource limits and capacity

Per store: WordPress 512 MB / 1 CPU limit, MariaDB 384 MB, agent 256 MB (it loads WordPress with all plugins for the store's cron every minute). Measured idle use for this stack is typically 250–400 MB in total; limits cap a busy or broken store, they are not reservations. Disk: ~150 MB for core and images per store (images are shared between stores on one version) plus the store's uploads and database.

<a id="capacity"></a>The Coolify API does not report the VPS's CPU, RAM or disk. The owner's notes give **8 vCPU, 32 GB RAM, 387 GB disk** (Ubuntu 24.04). Assuming the ~20 existing resources use 6–8 GB and keeping 30% of RAM free for peaks:

| Basis | Normal stores |
|---|---|
| Typical use, ~350 MB per store | **35–45** |
| Every store at its limits at once (~1.15 GB) | 13 |
| Disk, ~2–5 GB per store with uploads, database and snapshots in flight | 70+ (not the bound) |

Start with a soft cap of **35** stores on this server, watch real memory use, and adjust. CPU is shared and bursty; 8 vCPU is not the bound for low-traffic stores.

Past that, add a server to Coolify (`POST /servers` + validate) and point new stores at it with `COOLIFY_SERVER_UUID`. Existing stores move by snapshot and recreate on the new server. Above ~50 stores per server, one shared MariaDB per server with a database per store saves ~100 MB per store.

### Security

- **Isolation between stores.** Each store has its own containers, volumes, Docker network and generated database password. Store containers are not on Coolify's shared `coolify` network (`connect_to_docker_network: false`), so they cannot reach the WaaS API, its Postgres or the other apps on the VPS by container name. They share the kernel with everything else on the VPS: this is container isolation, adequate for normal stores, not for regulated ones, which go to their own server (`docs/hosting.md`).
- **No tenant shell.** The agent runs only commands the driver composes from validated input: ids are UUIDs, domains pass `normalizeDomain`, options and constants travel as JSON in an environment variable or base64 argument, never spliced raw into a shell string.
- **Secrets.** Private constants and the first user's password stay encrypted with `SECRETS_KEY` in Postgres as today and are decrypted only in the job that needs them. They reach the store as Coolify environment variables (encrypted at rest by Coolify), never in a scheduled-task command, a URL or a log line. The first user's password variable is deleted after the store's first boot. Database passwords are generated by Coolify (`SERVICE_PASSWORD_*`) and never pass through the API; the API's token cannot even read them back, since Coolify hides variable values from tokens without the sensitive-data permission. Pre-signed URLs do appear in task commands; they last 15 minutes and the task is deleted after it runs. The driver's errors carry Coolify's status and message, not request bodies.
- **Coolify token.** Coolify tokens are team-wide (no per-project scope). The API's token needs `read`, `write` and `deploy`; it should not have `root`. The driver refuses to touch any resource outside the configured project.
- **Cleanup on failure.** Every method is idempotent by name. A failed `createStore` leaves the Service for the queue's retry to reuse; a tenant that ends Failed is removed with `deleteTenant`, which deletes the Service and its volumes. A follow-up janitor job lists `WaaS Stores` Services with no matching tenant or version and reports them (it does not delete on its own).

## What Coolify cannot do, and the fill

| Gap | Fill |
|---|---|
| Exec in a container | On-demand scheduled task in the `agent` sidecar |
| Snapshot to S3 with files and DB together | `agent.php` with WP-CLI, pre-signed URLs |
| Suspend with 503 | Flag file read by an mu-plugin and `.htaccess` |
| Redirect domains with 301 | mu-plugin, by comparing the host to `home` |
| Wildcard certificates | Owner configures a DNS-01 resolver in Traefik |
| Server specs | Owner states the plan |

## Decisions for the owner

1. **Object storage:** Cloudflare R2 (recommended) or MinIO on Coolify? If R2: create bucket `waas-stores` and a bucket-scoped token, and add the four `S3_*` values to the WaaS API app.
2. **Store domain:** which domain (a separate registered domain is recommended), and set the `*.stores` and `*.versions` records (grey cloud).
3. **Wildcard TLS now or later?** Now means the Cloudflare DNS token and the proxy change above, with a short proxy restart.
4. **Store cap** on this VPS: a soft cap of 35 to start (from 8 vCPU / 32 GB / 387 GB)?
5. **Coolify token for the deployed API:** create one with read, write and deploy (not root) and add it as `COOLIFY_TOKEN` to the WaaS API app, plus `PROVISIONER=coolify` when ready.
6. **Smoke test:** OK to create project `WaaS Stores` and one throwaway store on `*.191.101.15.236.sslip.io`, deleted afterwards? It needs object storage for the snapshot step: R2 credentials in my environment, or a MinIO Service inside `WaaS Stores` for the test.
